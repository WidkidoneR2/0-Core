# .githooks

Tracked git hooks. Point git at them once per clone:

    git config core.hooksPath .githooks

## Why tracked, and why one command

`.git/hooks/` is NOT versioned, so a fresh clone has no hooks at all until someone remembers to
install them -- and nobody remembers. A tracked directory plus `core.hooksPath` makes the hooks
part of the repository, reviewed like any other file.

⚠️ THE ONE COMMAND IS THE COST, and it is deliberate. Git will not let a repository silently point
its own hooks at tracked, executable content -- that would let a clone run code before you read it.
Requiring the operator to opt in is the security property, not an oversight.

## What runs

Everything is `zero-gate`, which is in this repository and has no dependencies. It is silent on
success and reports anything it could not run rather than passing quietly.

    pre-commit   secrets, risk tiers, formatting
    pre-push     the shell test suite

## What this replaced

A `.pre-commit-config.yaml` GENERATED by `git-hooks.nix`, whose every entry was an absolute
`/nix/store` path. Off NixOS those do not resolve, and the framework SKIPS hooks it cannot find --
so all four gates would have vanished silently on a new distribution, with no message.

## ⚠️ THIS IS THE THIRD ATTEMPT. THE FIRST TWO DIED THE SAME WAY.

`flake.nix` records it in its own shellHook, and it is worth reading before trusting anything here:

> THE SAME BUG TWICE: INT-113 retired faelight-hooks on 2026-07-10 for being "dead weight: never
> installed into .git/hooks". INT-119 replaced it with a mechanism that is ALSO never installed
> into .git/hooks -- the identical defect, re-shipped under a new number, with "unskippable"
> written in the comment.

And what the measurement showed when someone finally looked:

    ls .git/hooks/pre-commit      -> No such file or directory
    cargo fmt --all -- --check    -> 114 unformatted files

> Nothing was ever skipped because nothing ever ran. ~30 commits landed on 2026-07-16 alone with
> zero complaints.

★ SO THE FAILURE MODE IS NOT "THE GATE WAS WRONG". It is "the gate was never invoked, and its
comment said otherwise". Both times the check was defined, the input imported, the comment
confident -- and the one line that does the work was missing.

## What is different this time, stated as evidence rather than confidence
- **It refused two real commits before it ever passed one.** The secrets scanner was reachable only
  as an absolute store path, so `zero-gate` reported UNKNOWN and stopped the commit. Twice. A hook
  that is not installed cannot refuse anything -- refusal IS the proof of installation.
- **It went green only after the environment was actually fixed**, by installing the tool through
  cargo and putting that directory on PATH. The gate was never loosened to reach success.
- **`core.hooksPath` is checkable in one command**: `git config core.hooksPath` prints
  `.githooks` or prints nothing. The previous mechanisms depended on a devShell sourcing a
  shellHook, which is true or false somewhere a reader cannot see.

⏭ THE OLD MECHANISM IS STILL IN `flake.nix` AND THAT IS DELIBERATE. It is inert -- `core.hooksPath`
overrides `.git/hooks/` entirely -- but it stays until this one has survived a week of real
commits. Deleting the fallback before the replacement has a track record is how the second attempt
became the third.
