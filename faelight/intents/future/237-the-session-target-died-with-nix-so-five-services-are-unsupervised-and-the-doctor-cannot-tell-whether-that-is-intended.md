## Vision

Whatever is supposed to run in the background is declared somewhere, and
something supervises it.

## The Problem

The doctor has reported System Services as UNKNOWN since 26 August, with the
message "could not read faelight-session.target wants". The check is correct
and the target is gone.

INT-222 rewrote that check on a good principle: ASK systemd which services
should be running rather than naming them in the code. The hardcoded list said
three -- notify, bar, wsd -- while the target actually wanted five, so
faelight-insightd had been invisible to the panel for weeks and faelight-idle
became invisible the moment it was wired. The fix made the target the source
of truth.

THEN THE SOURCE OF TRUTH WAS DELETED. faelight-session.target lived in nix/,
which was removed wholesale on 2026-08-28 as part of the Omarchy migration.
Nothing recreated it. git log finds no file by that name in history because
the unit was generated by a Nix module rather than committed as a file.

MEASURED 2026-09-01: systemctl --user lists no faelight service of any kind,
and faelight-daemon is not running. Five services that used to be supervised
are unsupervised, and nothing noticed because the check that would have said
so lost the ability to ask.

⚠️ THE CHECK IS NOT THE BUG. Zero wants correctly reports Unknown rather than
0/0 healthy, which is the free pass INT-222 exists to remove. Deleting the
check would hide this rather than resolve it.

## The Solution

THE QUESTION IS WHICH SERVICES SHOULD EXIST AT ALL, and it has to be answered
before anything is written. The five are not equal on Omarchy:

  faelight-daemon      Friday's persistent process -- INT-039 territory
  faelight-insightd    was doing real work, invisible for weeks even before
  faelight-notify      Omarchy has its own notification daemon
  faelight-bar         Quickshell and Waybar do this now -- likely redundant
  faelight-idle        was wired and immediately invisible

At least two look redundant on the new platform. At least one looks like it
should be running and is not.

DECIDE PER SERVICE, then declare what survives. A systemd user target is the
obvious mechanism and it is what the check already reads, so recreating one --
as a committed unit file this time, not a Nix-generated one -- would restore
the check without changing it.

## Success Criteria

- [ ] Each of the five is ruled KEEP or RETIRE, with a reason, measured
      against what Omarchy already provides rather than against what NixOS
      used to
- [ ] Whatever survives is declared in a committed unit file, so deleting a
      directory cannot silently remove the declaration again
- [ ] The doctor's System Services check goes from Unknown to a real reading
      WITHOUT modifying the check -- it asks systemd, so restoring the target
      is the whole fix
- [ ] Retired services are removed from the registry and from anything that
      expects them, not merely left unstarted
